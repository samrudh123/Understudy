# Decision log

Every non-obvious choice, why it was made, and what was rejected. Newest at the bottom.
Problems hit during the build are logged as **Problem** entries.

| # | Date | Decision | Rationale | Alternatives considered |
|---|------|----------|-----------|-------------------------|
| 1 | 2026-11-05 | **CLINC150** as the core dataset | 150 intents across 10 domains, so whole domains can be held back to create real drift. A dedicated out-of-scope set tests whether the router passes questions on correctly. | Banking77 (no OOS set, one industry), a campus FAQ (synthetic logs weaken the mining and drift story) |
| 2 | 2026-11-05 | Dataset pinned to upstream commit `828f809` + SHA-256 | Reproducibility: `ingest_dataset` fails loudly if the bytes ever change | `dvc import-url` (also fine, but a checksum in `params.yaml` is visible and reviewable) |
| 3 | 2026-11-05 | All training and inference **on this machine** (16 cores, 31 GB RAM, no CUDA) | The course disallows cloud platforms. CPU is enough for a MiniLM student and a 1.5–3B Q4 teacher. | Colab/cloud GPUs (not allowed) |
| 4 | 2026-11-05 | Answer bank is **rebuilt from `data/approvals/*.json`** (one file per FAQ, in Git) | `mine_frequent` must know what is already approved, and `approve` produces the bank. Making the bank a pure function of the approval history keeps the DVC graph acyclic. Each decision is also an auditable Git diff. | Mutating one bank file in place (creates a DAG cycle; history only in DVC cache) |
| 5 | 2026-11-05 | Log de-duplication on `request_id`, **not** on text | Repeated questions *are* the frequency signal that mining needs. Only true duplicates (retries, double writes) are removed. | Text de-dup (would destroy the frequency signal) |
| 6 | 2026-11-05 | PII scrubbed **at write time** (QueryLogger) **and again** in Spark preprocess | Raw personal data never reaches disk. The second pass catches anything written by older code. | Scrub only in the pipeline (raw PII would sit on disk) |
| 7 | 2026-11-05 | Traffic simulation: Zipf popularity, scheduled domain arrival with a 2-week surge, 5% OOS, 2% injected PII | Matches the helpdesk pattern (a few questions dominate) and creates a measurable drift event in week 3 | Uniform sampling (no "frequent" questions to mine) |
| 8 | 2026-11-05 | Offline simulator routes with an **oracle** (true intent ∈ approved bank → student) | Lets the data pipeline be built and tested before the edge service exists. Records are marked `source=simulated`, `student_version=oracle`. Phase 4 replaces this with real `/ask` calls. | Waiting for the edge service before testing the pipeline |
| 9 | 2026-11-05 | Mining = MiniLM embeddings (Spark `mapInPandas`) + Spark ML **KMeans (cosine, count-weighted)**, k chosen by silhouette | Uses the same encoder as the student, so "similar" means the same thing in both places. Weighting by count makes frequent questions pull centroids. Silhouette removes a hand-tuned k. | TF-IDF + KMeans (weaker on paraphrases), DBSCAN/HDBSCAN (not in Spark ML) |
| 10 | 2026-11-05 | Clusters near an approved FAQ are flagged `known_but_missed`, not re-mined | They show the student's τ is too strict, not that knowledge is missing. That is a different fix. | Treating every fallback cluster as new knowledge |
| 11 | 2026-11-05 | Batch stages push metrics to a Prometheus **Pushgateway** and also write `reports/stages/<stage>.json` | Short-lived jobs can't be scraped. The JSON reports feed the pipeline console and work even when monitoring is down. | Scraping a long-running pipeline daemon |
| 12 | 2026-11-05 | Hashing encoder (`hash:<dim>`) for tests | Unit and integration tests run offline, deterministically and fast. The real MiniLM is pinned by HF revision in `params.yaml`. | Downloading MiniLM in CI |
| 13 | 2026-11-05 | CI = Git hooks: **pre-commit** (ruff + unit tests), **post-commit** (`scripts/ci.sh`: lint, all tests, `dvc repro`) | Satisfies "continuous integration using DVC" without a hosted CI runner. Confirm with the instructor (proposal B9 Q2). | GitHub Actions (hosted runner; not needed for a local-only project) |
| 14 | 2026-11-05 | Mining **over-clusters** (avg distinct-questions per cluster 10–20) then **merges centroids ≥ 0.75 cosine** | Offline sweep on weeks 0–1 (4,000 fallbacks): silhouette is flat (0.15–0.19) on short-text embeddings and alone picked k=39, giving purity 0.71. Over-clustering + merge gives purity ≈ 0.85–0.88. Purity matters more than duplicates: a mixed cluster yields a wrong teacher answer for part of its questions, while a duplicate topic can be merged into an existing FAQ at approval. | Silhouette-only k (purity 0.71); higher merge threshold (more duplicates, lower coverage) |
| 15 | 2026-11-06 | Teacher = **Qwen2.5-3B-Instruct Q4_K_M** (GGUF, 2.1 GB) on CPU llama.cpp, pinned by HF commit + SHA-256 | Measured on this machine (8 threads): TTFT p50 0.54 s / p95 0.76 s once warm (about 3.8 s cold, the first system-prompt prefill), about 14 tok/s, about 2.2 s for a typical answer (`reports/teacher_baseline.json`). That is fast enough for live fallbacks and for `distil` (about 18 s per FAQ draft). | Qwen2.5-1.5B (faster, weaker answers; a one-line swap in `params.yaml`), 7B (about 3x slower on CPU) |
| 16 | 2026-11-06 | Ray Serve deployment with **`max_ongoing_requests=1` per replica** | A llama.cpp context is not thread-safe. Ray Serve queues extra requests and gives back-pressure. Scale with replicas x threads. | A custom asyncio lock inside one replica (hides the queue from Ray's metrics/autoscaler) |
| 17 | 2026-11-06 | The gateway **waits for the first token before sending the response status** | Failures keep real status codes (`503` teacher down, `504` no first token in `first_token_timeout_s`), so the edge can degrade cleanly. After that, errors arrive as an SSE `error` event. The UI is not blocked: the edge already shows the "while you wait" card. | Streaming `200` immediately (every failure becomes an in-band event, which is harder to monitor) |
| 18 | 2026-11-06 | `distil` and `grade` use **grammar-constrained JSON** (llama.cpp `response_format` with a JSON schema) | Output is always parseable. No regex repair of LLM output. | Free-text parsing with retries |
| 19 | 2026-11-06 | **Heuristic prompt-injection guard** in the gateway, plus "treat the message as a question" in the system prompt | Simple, explainable and unit-tested (including false positives like "what are the rules for carry-on luggage"). Only the teacher needs it: the student can only return pre-approved answers. | An LLM-based classifier (doubles teacher load) |
| 20 | 2026-11-06 | `FakeEngine` (`UNDERSTUDY_TEACHER_FAKE=1`) with the same interface as llama.cpp | Unit tests, CI and the Compose smoke test run in seconds without the 2 GB model. Real-model tests are integration tests that skip when the weights are absent. | Mocking HTTP everywhere |
| 21 | 2026-11-06 | Student encoder = MiniLM exported **once** to ONNX (pooling + L2 norm in the graph), dynamic **per-channel UINT8** | 86 MB → 22 MB; 4.7 ms per question on one thread. Per-tensor INT8 kept only cosine 0.96 to fp32 and changed 20% of nearest neighbours. Per-channel UINT8 keeps cosine 0.99 and 94% neighbour agreement (`reports/encoder_export.json`). Training embeds with this same INT8 graph, so there is no train/serve skew. | Fine-tuning the encoder (slower, needs more data); quantising after training (the head would be trained on different embeddings) |
| 22 | 2026-11-06 | `distil` runs its **own Ray actor pool** of llama.cpp models, not calls to the live teacher | The pipeline works when the serving stack is down and does not steal live capacity. Drafts are cached by (model, prompt version, examples), so re-runs are free. Measured about 4 drafts/min with 2 actors x 7 threads. | Calling the Ray Serve teacher over HTTP (couples batch to serving) |
| 23 | 2026-11-06 | Approvals: approve / reject / **merge into an existing FAQ**, plus a clearly-labelled **simulated reviewer** (`approve auto`) | Mining over-clusters on purpose (decision 14), so duplicates are merged at review time. Their phrasings become extra training data. The simulated reviewer uses the simulation ground truth so demos and tests run unattended. Real reviews go through the console. | Auto-approving everything (teacher mistakes reach users, e.g. it said Las Vegas is on Mountain time) |
| 24 | 2026-11-06 | **Log negatives**: fallback questions with cosine < 0.55 to every approved phrasing become `__fallback__` training examples | Teaches the student what it does not know, using no labels. Measured label noise 10%. In a sweep, 0.65 gave 21% noise and coverage collapsed to 0.27, and 0.75 gave 31% noise. | OOS set only (does not cover in-domain but un-approved intents) |
| 25 | 2026-11-06 | Gate on **traffic-weighted precision** (test questions weighted by each intent's share of recent traffic). The uniform CLINC test is reported as a stress test. | The CLINC test set is uniform over 150 intents, so uncovered intents outnumber covered ones 6:1. That is far from live traffic. Champion v1: traffic precision 0.993 / coverage 0.81. Uniform: 0.84. Uniform errors are mostly neighbouring intents ("transfer my 401k" → money-transfer FAQ). Shadow grading (Phase 6) measures live precision directly. | Gating on uniform precision (would reject a model users find 99% precise) |
| 26 | 2026-11-06 | τ is tuned on validation to **stricter** targets (precision 0.97, false-accept 0.03) than the gate (0.95 / 0.05). The gate also requires traffic coverage ≥ 0.30. | Leaves a safety margin for validation→test shift. The coverage floor exists because a student that never answers trivially meets every precision target (a unit test caught this). | Same targets for tuning and gating |
| 27 | 2026-11-06 | Ray Tune random search (32 trials) over **logreg / MLP / centroid** heads with an optional fallback class. Every trial is a nested MLflow run. | Takes about 25 s on 8 CPUs. In the first run 26 of 32 trials were feasible and logistic regression (C≈1) with a fallback class won. Heads run in numpy, so the edge needs no sklearn or torch. | Grid search; a single fixed head |
| 28 | 2026-11-06 | Student logged as an MLflow **pyfunc from code** (`student/pyfunc_entry.py`), with the artifacts dir shared by `models/student/` | The registry holds a self-describing model. The edge downloads the same artifact directory and runs `StudentPredictor` directly, without MLflow's pyfunc environment. | A pickled `PythonModel` (failed: an ONNX session cannot be pickled, see P3) |
| 29 | 2026-11-06 | Edge loads the champion by **downloading the artifact directory** for `models:/understudy-student@champion` and running `StudentPredictor` directly. A background loop retries until a champion exists. `/admin/reload` hot-swaps under a lock. | No MLflow pyfunc environment at the edge: the image has onnxruntime + tokenizers + mlflow-skinny and uses 87 MB RAM. The old model keeps serving if a reload fails. With no model, every question goes to the teacher (degraded but working). | `mlflow.pyfunc.load_model` at the edge (heavier; code-path shadowing risk) |
| 30 | 2026-11-06 | **Opportunistic micro-batching** at the edge | Under 8 concurrent clients on 1 CPU, one ONNX call per request let threads fight over the CFS quota: p95 was 189 ms. Batching what is already queued into one encoder call, with no artificial wait, gives p95 71 ms concurrent and 10.8 ms sequential. A fixed 2 ms batching window doubled the sequential latency, so it was dropped. | No batching; a fixed batching window |
| 31 | 2026-11-06 | `/ask` always streams SSE `meta → token… → done/error`. Instant answers arrive as one token. Fallbacks send the "while you wait" card and related FAQs in `meta` **before** calling the gateway. | One protocol for the UI. The filler card appears within milliseconds whatever the teacher is doing. `stream=false` returns JSON for scripts and simulation. | Separate endpoints for instant and streamed answers |
| 32 | 2026-11-06 | **Online simulation** replays weeks against the real `/ask`, but only a sample (`--teacher-rate`, default 1%) of fallbacks actually calls the CPU teacher | Exercises real student routing, logging and metrics at about 80 qps. Generating 1,000 teacher answers per week would take hours on CPU and adds nothing to the drift signal. Simulated requests carry ground truth and deterministic request ids, so replays de-duplicate. | Calling the teacher for every fallback |
| 33 | 2026-11-06 | The **simulated clock** defines "recent" for mining and traffic weights when simulated traffic exists | Live questions carry real timestamps (week ≈ 13 relative to the simulation start), which would otherwise hide all simulated weeks. Live questions always count as recent. | A separate clock service |
| 34 | 2026-11-06 | Drift alert → Alertmanager → console webhook starts **discovery only** (`dvc repro distil`), with a cooldown. Retraining waits for a human approval. | Matches the human-in-the-loop requirement: the teacher drafts, a person approves. Retraining on unapproved drafts would ship unchecked teacher mistakes. | Fully automatic retrain on alert |
| 35 | 2026-11-06 | Ratios (fallback, error, shadow agreement) are Prometheus **recording rules** over counters, not gauges exported by the services | Survives restarts, aggregates across replicas, and the window (2 min for the demo) is changed in one place. Mapping to the proposal's metric names is in `docs/test_plan.md`. | `understudy_fallback_ratio` gauge in the edge |
| 36 | 2026-11-06 | The console runs pipelines **inside the pipeline image against the bind-mounted repo** (uid 1000), one at a time | Same environment as CI. DVC/Git state stays on the host and is visible to the developer. A lock prevents two `dvc repro` runs racing for the registry. | A separate Airflow/worker service (more moving parts) |
| 37 | 2026-11-06 | nginx terminates **TLS** with a self-signed certificate generated at first start, proxies `/api/edge/` (SSE unbuffered) and `/api/console/`, and **blocks `/api/edge/admin/*`** | HTTPS by default. Admin reloads are only reachable inside the Docker network (register stage, console). The optional `UNDERSTUDY_ADMIN_TOKEN` adds a second factor. | Exposing services directly |
| 38 | 2026-11-06 | Grafana dashboard **generated from code** (`scripts/build_dashboard.py`), provisioned read-only. Per-service CPU/memory come from each service's own `ProcessCollector`. | A reviewable diff instead of a hand-edited JSON blob. Process metrics show the edge staying inside its 1 CPU / 1 GiB budget (≈180 MiB RSS). cAdvisor was tried and dropped (P9). | Hand-built dashboard exported from the UI; cAdvisor |
